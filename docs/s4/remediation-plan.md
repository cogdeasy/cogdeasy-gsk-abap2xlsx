# S/4HANA clean-core remediation plan (draft)

Draft example for GSK's SAP team. Analysis only: built from `docs/s4/readiness-inventory.md`
(generated by `tools/s4_inventory.py`) and from reading the source. Nothing here was run on an
SAP system. Devin drafts briefs and fix PRs; GSK's SAP team decides and executes. No Basis work,
data migration or system conversion.

## Starting point

- 272 objects, 45,452 source lines: 72 classes, 11 interfaces, 1 program, 2 simple
  transformations, 1 message class, 185 DDIC objects. No function groups.
- Two folders: `src/` (244 objects) and `src/not_cloud/` (28 objects, package text "Objects
  which cannot work in SAP Cloud").
- Simplification-item risk is low: the only SAP tables read are `DD07T`, `SEOCLASS`,
  `SEOCOMPODF`, `TFDIR`, `TFO01`, `TCURX`, `T006` and `USR01`. No FI/CO, MM or SD tables.
- Clean-core risk is the main driver: 33 calls to SAP function modules, 11 direct selects on
  SAP tables, 18 `cl_gui_*` references.
- Cross-check: `npx abaplint abaplint-steampunk.json` (ABAP Cloud syntax, steampunk-2205 API,
  `not_cloud/` excluded) reports 268 warnings in `src/` (136 `check_syntax`, 112
  `unknown_types`, 20 `parser_error`). It also flags items the inventory does not pattern-match:
  `cl_ixml` / `if_ixml*`, `cl_abap_conv_in_ce` / `cl_abap_conv_out_ce`, `DESCRIBE FIELD`,
  `cl_salv_table` in `ZCL_EXCEL_COMMON`. This is a warning-level check, separate from the
  `npm run lint` gate.

## Wave summary

| wave | scope | objects | occurrences | decision needed |
|---|---|---|---|---|
| 1 | mechanical syntax | 14 (11 in `src/`, 3 in `not_cloud/`) | 157 | rule change in `abaplint.json`, after wave 3 decides on `not_cloud/` |

three). Within a wave, child sessions are split by object group so their PRs do not overlap.

## Wave 1: mechanical syntax

**Objects:** `ZCL_EXCEL`, `ZCL_EXCEL_COMMON`, `ZCL_EXCEL_FONT`, `ZCL_EXCEL_READER_2007`,
`ZCL_EXCEL_ROW`, `ZCL_EXCEL_TABLE`, `ZCL_EXCEL_WORKSHEET`, `ZCL_EXCEL_WRITER_2007`,
`ZCL_EXCEL_WRITER_CSV`, `ZCL_EXCEL_WRITER_HUGE_FILE`, `ZCL_EXCEL_WRITER_XLSM`; in `not_cloud/`:
`ZCL_EXCEL_CONVERTER`, `ZCL_EXCEL_OLE`, `ZEXCEL_TEMPLATE_GET_TYPES`.

**Findings:** 141 obsolete statements (`ADD` 116, `SUBTRACT` 13, `PERFORM` 5, `FORM` 4,
`SEARCH` 3) and 16 `WRITE ... TO`. No `OCCURS`, header lines or list output.

**Sample:** `src/zcl_excel_common.clas.abap:829` `WRITE lv_pwd_hash TO r_encrypted_pwd.` The
ABAP Cloud lint reports it as "Statement does not exist in the configured ABAP version".

**Approach:**

- `ADD x TO y` becomes `y = y + x`; `SUBTRACT` likewise. Check the operand types of each
  statement; most are integer counters.
- `WRITE ... TO` becomes a string template with the same formatting option (`NUMBER`, `DATE`,
  `TIME`, `EXPONENT`, `CURRENCY`). Each needs a unit test: formatting depends on user settings.
- `DESCRIBE FIELD` (2, from the Cloud lint, `ZCL_EXCEL_WORKSHEET`) becomes RTTI
  (`cl_abap_typedescr=>describe_by_data( )`).
- `FORM` / `PERFORM` / `SEARCH` are only in `not_cloud/` objects; do them only if wave 3 keeps
  those objects.
- `abaplint.json` currently allows `ADD` / `SUBTRACT` (`"add": false, "subtract": false`) and
  `AGENTS.md` says not to tidy upstream ABAP without a ticket, so wave 1 needs its own ticket.
  The rules are switched on only after the 28 `ADD` statements in `not_cloud/` are gone (session
  1d, or the SAP team retires those objects in wave 3); `abaplint.json` lints `not_cloud/` too, so
  switching them on earlier would fail the 0-issue gate.

**Findings:** 19 SAP function-module calls, 1 dynamic `CALL FUNCTION`, 4 selects on SAP tables,

Release status must be confirmed in SAP's Cloudification Repository before any PR.

## Wave 3: SAP GUI, ALV and OLE dependencies

**Objects:** `not_cloud/`: `ZCL_EXCEL_CONVERTER`, `ZCL_EXCEL_CONVERTER_ALV_GRID`,
`ZCL_EXCEL_CONVERTER_SALV_TABLE`, `ZCL_EXCEL_OLE`, `ZEXCEL_TEMPLATE_GET_TYPES`; `src/`:
`ZCL_EXCEL_READER_2007`, `ZCL_EXCEL_WORKSHEET`.

**Findings:** 18 `cl_gui_*` references (`CL_GUI_FRONTEND_SERVICES` 10, `CL_GUI_ALV_GRID` 6,
`CL_GUI_CONTAINER` 2) and 7 GUI/ALV function-module calls (`LVC_*` 4, `LT_VARIANT_LOAD`,
`POPUP_GET_VALUES`, `GUI_HAS_ACTIVEX`). `ZCL_EXCEL_OLE` also selects `TCURX`, `T006`, `USR01`.

**Sample:** `src/zcl_excel_reader_2007.clas.abap:4129` `read_from_local_file` calls
`cl_gui_frontend_services=>gui_upload`, so the core reader package depends on SAP GUI.

**Approach:** these are design decisions, not syntax fixes. For each object group Devin writes a
brief with three options and their effect on callers: keep as classic code in `not_cloud/`
(works on S/4HANA with SAP GUI, outside clean core), replace (caller supplies the file as
`xstring`; Fiori or an API delivers it), or retire (no known callers). For the two `src/`
touchpoints the low-risk option is to move them into `not_cloud/`: `read_from_local_file`
behind `zif_excel_reader~load_file`, and `bind_alv_ole2` (`src/zcl_excel_worksheet.clas.abap:148`,
which already calls `ZCL_EXCEL_OLE` dynamically). Code changes start only after the SAP team
picks an option.
